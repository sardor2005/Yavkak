# ЯВКА — MVP 1.0

Доработка существующего React-приложения `sardor2005/Yavka` с сохранением логотипа, русского интерфейса, фирменных CSS и карточек. Backend — Supabase Auth/PostgreSQL/Storage/Realtime, frontend — Vite, размещение — существующий Vercel Hobby.

Облачный Supabase-проект ещё не создан владельцем. Изменения MVP в production не публиковались; существующий публичный deployment не проверен. Реальные пользовательские данные не заменяются Demo. Состояние фактических проверок — в [docs/TESTING.md](docs/TESTING.md).

## Быстрый запуск

Требуется Node.js 22.12+ (текущая среда — Node.js 24). Установка использует сохранённый lockfile:

```bash
npm ci
cp .env.example .env.local
```

В `.env.local` добавьте URL и публичный publishable key своего тестового Supabase:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
```

Затем примените миграции и настройте Auth по [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

```bash
npm run dev        # Vite, http://localhost:5173
npm run build      # production-сборка dist/
npm run preview    # проверка сборки на http://localhost:4173
npm run check      # сборка, 23 локальные проверки и SQL/RLS
npm run test:e2e   # браузерные проверки Playwright
```

Привилегированные ключи, пароли базы и `service_role` не должны попадать в переменные `VITE_*`, frontend или Git. Publishable key публичен; безопасность обеспечивают проверенные RLS и серверные операции. Без настроенного backend приложение сообщает о необходимой конфигурации и не создаёт демонстрационные аккаунты.

## Локальный Supabase без облачного проекта

Для полного локального сценария нужен работающий Docker daemon. CLI Supabase закреплён в devDependencies; отдельная платная инфраструктура не требуется.

```bash
npx supabase start --exclude studio,postgres-meta,edge-runtime,logflare,vector,supavisor,imgproxy
npm run dev:local           # публичные URL/key из локального CLI, без .env
npm run test:integration    # три настоящих локальных Auth-аккаунта и HTTP/RLS
npm run test:e2e:live        # два независимых браузерных контекста
npx supabase stop           # остановить только локальную среду этого проекта
```

Если ECR запрещён политикой сети, официальный поддерживаемый mirror выбирается через `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io`. Не отключайте TLS, проверку checksum и RLS. Подробности локальной среды и фактические результаты — в [docs/TESTING.md](docs/TESTING.md).

`test:sql` применяет миграции в настоящем PostgreSQL через PGlite с тестовыми схемами Auth/Storage. Это проверка SQL/RLS, которая не заменяет HTTP/Auth/Storage/Realtime. Без локального Supabase `test:e2e` проверяет экран конфигурации; два общих сценария встречи явно пропускаются.

## Состав MVP

1. Email/password Auth, подтверждение email, восстановление пароля/сессии и собственный профиль.
2. Встречи с фиксированным временем и timezone, организатором, участниками, историей, отменой и завершением.
3. Приглашения друзьям и по случайному серверно проверяемому токену со сроком действия/отзывом.
4. Отдельные состояния приглашения и ручного прибытия с серверным временем.
5. Фотографии участников в приватном bucket `meeting-photos`: JPEG/PNG/WebP, до 2 МиБ и до 6 фото на встречу, авторское удаление.
6. Экспериментальный серверный рейтинг на основе ручных отметок, защита от повторного начисления и отмена ошибок.
7. Поиск публичных профилей, заявки и друзья без раскрытия email.
8. Текстовый чат встречи, история, авторское удаление и Realtime только для разрешённых данных.

Основной сценарий двух независимых аккаунтов прошёл на настоящем локальном Supabase в desktop/mobile браузерах. Облачный Supabase, SMTP и публичный Vercel deployment требуют отдельной настройки и проверки владельцем; подробный охват — в отчёте тестирования.

Прежнего расчёта рейтинга в предоставленном исходном коде нет. Новое экспериментальное правило применяется при завершении к принявшим участие: **+10** за ручную отметку прибытия не позже начала, **0** за опоздание, **−5** за отсутствие отметки. До начала встречи завершение запрещено. Клиент не задаёт суммы баллов. Результат не подтверждается GPS. Изменение правила должно выполняться согласованной серверной миграцией, а не прямой записью итогового счёта из браузера.

## Что сохранено и отложено

Исходная браузерная beta сохранена в `legacy/beta/` и истории Git. В ней были локальные варианты/голосование, снимок приглашения в URL, переключение Demo и localStorage. В активном MVP используется общий Supabase; старые записи не импортируются автоматически в реальные аккаунты и не удаляются при настройке backend.

GPS, ИИ-гид, коллекция достопримечательностей, погода/ETA и push не входят в MVP. Они не найдены как работающие модули исходного приложения; об их удалении из прежнего интерфейса не заявляется. Чат не поддерживает голос, видео и файлы. Подробнее: [docs/DEFERRED_FEATURES.md](docs/DEFERRED_FEATURES.md).

## Основные файлы

- `src/context/AuthContext.jsx` — Auth-сессия и профиль.
- `src/context/AppContext.jsx` — загрузка общего состояния и сообщения об ошибках.
- `src/services/supabase.js` — клиент из публичной Vite-конфигурации.
- `src/services/api.js` — обращения к RLS/API и доверенным RPC.
- `src/pages/` — существующие страницы и новые Auth, друзья, приглашения, профиль.
- `src/styles.css`, `src/meeting.css`, `src/mvp.css` — фирменный дизайн и необходимые расширения.
- `supabase/migrations/` — схема, серверные функции, RLS, Storage и Realtime.
- `tests/`, `e2e/`, `supabase/tests/` — локальные, браузерные и SQL/RLS-проверки; фактический охват указан в отчёте.
- `public/brand/yavka-logo.jpg` — существующий оригинал логотипа.
- `legacy/beta/` — архив исходной локальной beta, не подключённый как production backend.

## Что сделать владельцу

1. Проверить изменения/PR в GitHub; самостоятельно решить вопрос merge.
2. Создать Supabase Free, применить три миграции, проверить приватный bucket и RLS.
3. Включить подтверждение email и проверить доставку писем. Добавить `/auth/callback` и `/auth/reset` для существующего домена и используемых тестовых адресов.
4. Добавить два публичных параметра в существующий Vercel-проект, проверить preview.
5. На двух устройствах зарегистрировать независимые аккаунты и пройти общий сценарий встречи, друзей, чата, статусов, фото и рейтинга. Проверить запреты для постороннего аккаунта.
6. Выполнить production deployment после проверки и настроить ручное резервное копирование базы **и** объектов Storage.
