# Проверки MVP «Явка»

Этот документ фиксирует фактические проверки отдельно от ожидаемых сценариев. Положительные unit-тесты или успешная сборка не доказывают корректность RLS, доставки email и синхронизации настоящих аккаунтов между устройствами.

Сохранены исходная история приложения из `Yavka` и история целевого репозитория; прежние подготовительные документы находятся в `legacy/repository-onboarding/`. Они не объявляются повторным запуском из нового каталога; результаты такой проверки фиксируются отдельно после её завершения.

SQL/RLS не ослаблялись, задержка и ручной polling не заменяют проверку WebSocket-доставки.

## Запуск live проверок

```bash
npm ci
npx supabase start --exclude studio,postgres-meta,edge-runtime,logflare,vector,supavisor,imgproxy
npm run test:integration
npm run test:e2e:live
npm run dev:local
```

Runner читает сгенерированные локальные ключи из `supabase status --output json` в памяти и не выводит их в лог. Privileged key попадает только в Node/Playwright-процесс для создания, сдвига времени и удаления fixture; браузеру передаются лишь URL и публичный anon key. Запуск против cloud намеренно отвергается. Не используйте административную сессию для доказательства RLS.

При запрещённом ECR поддерживаемый официальный mirror — `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io`. Первый Docker pull PostgreSQL на текущем managed Docker с драйвером `vfs` исчерпал диск 32 ГиБ (`failed to register layer: no space left on device`); загрузка остановилась, место освободилось. Проблема решена компактным однослойным импортом файловой системы того же официального образа: проверены checksum инструмента crane, manifest и все layer digests; сохранена runtime-конфигурация, включая healthcheck. Образ занимает около 2,7 ГБ. Полный локальный Supabase запущен, миграции применены, реальный HTTP/Storage/WebSocket runner прошёл. В `/workspace/.cloud-setup/yavka/` сохранены локальные install/start helpers; они относятся к настройке этой среды, а не production-образу приложения.

## Ограничения безопасности и эксплуатации

SQL rate limits: создание встреч — 20/сутки, заявки друзей — 20/час, приглашения — 30/час, чат — 1/секунду и 30/минуту, изменение ответа и прибытия — по 20 изменений/минуту на пользователя и операцию. Одинаковые повторы статуса не создают событий и не расходуют этот лимит. Общего SQL-лимита поиска и редактирования профиля нет; ограничения проекта/API и Auth задаются отдельно в cloud.

Триггер на управляемой `storage.objects` требует проверки при изменении версии Storage. Он не имеет исключения для окончательной внутренней административной записи. Подготовка fixture и смена времени встречи администратором используются только для изолированных тестов и не доказывают клиентские права.

Приложение загружает приватные фото через authenticated download и временные Blob URL. Ранее скачанный файл нельзя отозвать с чужого устройства; самостоятельно выданный через разрешённый SDK signed URL действует до TTL. Удаление участника прекращает последующие авторизованные чтения. Реальные cloud Realtime-подписки и их прекращение необходимо проверить отдельным аккаунтом.

## Проверка после настройки Supabase

Создайте минимум три независимых тестовых пользователя: организатор A, участник B и посторонний C. Для принятия и смены статусов используйте обычные пользовательские сессии. `service_role` обходит RLS и не подходит для доказательства безопасности политики.

Обязательный общий сценарий: A и B регистрируются на разных устройствах, подтверждают email, находят друг друга, становятся друзьями, создают и принимают приглашение на одну встречу, переписываются, меняют ручные статусы, загружают фото, завершают встречу и проверяют рейтинг. После выхода/повторного входа данные сохраняются. C не видит приватную встречу, чат, фотографии и приватные поля профиля.

Дополнительно проверить:

- Просроченную, отозванную и повторно использованную ссылку; обычный UUID встречи не даёт доступ.
- Прекращение доступа после удаления участника, включая уже открытые подписки.
- Запрет удаления чужих фото/сообщений, изменения чужих заявок, добавления себя и дублей дружбы.
- Изменение плана, сброс отметок, отмену встречи, повторное завершение и отмену ошибочного результата рейтинга.
- Конкурирующие запросы, уникальность результатов, лимиты фото/сообщений и rate limits.
- Пагинацию истории; восстановление после потери сети без пропущенных или дублирующихся сообщений.
- Доставку Auth-писем, exact redirect URL и восстановление пароля в реальном deployment.

Моки допустимы в unit/component-тестах, но их результаты должны оставаться отдельно от live интеграций. Фиксировать `passed`, `failed`, `skipped` и непроверенные сценарии явно.
