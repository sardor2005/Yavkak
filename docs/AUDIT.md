- `npm run dev` запускает Vite, `npm run build` создаёт `dist/`, `npm run preview` проверяет сборку. `npm test` использует встроенный `node:test`; `npm run test:e2e` — Playwright.

## Существующая модель и правила, которые необходимо сохранить

`src/services/storage.js` — единый синхронный сервисный слой. Компоненты вызывают его функции через `AppContext.mutate`; при подключении backend вызовы необходимо перевести на асинхронные операции и обработку ошибок. Нельзя возвращать фиктивный успех или оставлять локальное изменение основным источником данных.

Встреча содержит локальные `id`, `title`, `description`, `organizer`, `participants`, `timeOptions`, `placeOptions`, `status`, `confirmedTime`, `confirmedPlace`, `planVersion`, `photos`, `memoryNote`, `isDemo`, `createdAt`, `updatedAt`, `completedAt`. Организатор — один из участников. Идентификаторы имеют префиксы вроде `meeting-`/`person-`; это не готовые UUID/FK модели backend.

Важные существующие правила:

1. Этапы встречи: `planning` → `awaiting` при сохранённых голосах всех участников → `confirmed` → `completed`. Организатор вправе подтвердить план до получения всех голосов.
2. Варианты и голоса сохраняются отдельно от финального плана. Голосование требует хотя бы одного корректного варианта времени и места; дубли голосов удаляются.
3. При изменении **даты, времени, названия места или адреса** финального плана увеличивается `planVersion`; всем участникам сбрасываются `attendance = pending`, `arrivalStatus = home`, `lateMinutes = 0`. Голоса при этом сохраняются. Повторное сохранение неизменённого плана сохраняет ответы и версию.
4. `attendance`: `pending`, `going`, `maybe`, `declined`. `arrivalStatus`: `home`, `leaving`, `late`, `arrived`. При ответе, отличном от `going`, прибытие и задержка сбрасываются. Изменять прибытие можно только после подтверждения участия в подтверждённой встрече.
5. Пользовательская задержка — целое число от 1 до 180 минут. Это заявление участника, а не измеренное опоздание и не основание считать прибытие объективно подтверждённым.
6. Встреча ограничена восемью участниками; имена в одной локальной встрече проверяются на дубли без учёта регистра. Backend должен связывать участие с Auth UUID, не использовать имя как идентификацию.
7. Воспоминание доступно после завершения. Исходная версия позволяет редактировать его только организатору; требование MVP о фотографиях всех участников требует расширения этой модели с авторством и серверными правами.

Отмена встречи, удаление участника, серверное принятие/отклонение приглашения и отметка неявки в исходном приложении отсутствуют; это новые функции MVP.

## Старые правила рейтинга: отсутствуют

В `README.md` исходного коммита рейтинг пунктуальности перечислен среди намеренно отсутствующих функций. Поиск по исходникам и изучение сервисного слоя не выявили модели баллов, формулы расчёта, результатов пунктуальности или событий начисления. `lateMinutes` — выбранная пользователем задержка; `arrivalStatus` — строка ручного статуса. При отметке `arrived` не сохраняется отдельный timestamp прибытия.

Следовательно, **сохранить существующую числовую формулу невозможно: её нет в предоставленном коде**. Нельзя приписывать новому правилу происхождение из старой «Явки». Новая серверная реализация должна явно документировать свою экспериментальную формулу, источник времени, отмену ошибок, обработку отменённых встреч и защиту от повторного начисления. Результат основан на ручной отметке, а не на координатах или объективном подтверждении.

## localStorage, демонстрация и перенос данных

- `yavka:repository:v1`: JSON с `version: 1` и всеми локальными встречами, участниками, голосами, статусами, заметкой и фотографиями в data URL.
- `yavka:participants:v1`: соответствие ID встречи локально выбранному ID участника. Это не Auth-сессия и не доверенное право доступа.
- При отсутствии репозитория автоматически записывается `demo-yavka` с Сардором, Нуржигитом, Натальей, Данияром и Камилой; организатор становится текущей локальной ролью.
- `resetDemo()` заменяет весь локальный репозиторий на seed и сбрасывает роли. В интерфейсе есть подтверждающий диалог, но это уничтожает локальные пользовательские встречи и фото. В production такой механизм не должен затрагивать реальные серверные данные.
- `AppContext` слушает браузерное событие `storage`: это обновление между вкладками одного origin, не Supabase Realtime и не синхронизация разных устройств.
- При отказе localStorage, повреждённом JSON и превышении квоты сервис показывает ошибки, не перезаписывает повреждённые данные молча и не переключается в браузере на временное хранилище.

Доменные данные требуется перенести в Supabase. Старые демонстрационные или локальные записи нельзя автоматически привязывать к реальным аккаунтам. Уже существующие локальные записи не следует удалять без необходимого отдельного действия владельца. Настройки интерфейса и стандартное локальное хранение Auth-сессии допустимы отдельно от предметных данных.

## Приглашения и границы безопасности

`createInviteUrl()` создаёт `/join/<id>#invite=<base64url JSON>`. Снимок содержит название, описание, организатора, имена/ID участников, их голоса/статусы, варианты и финальный план. Это кодирование, а не шифрование или подпись. Фото и заметка в снимок не входят.

`importInvite()` валидирует форму данных и импортирует независимую копию; существующая отредактированная локальная встреча не перезаписывается. При импорте роль участника не выдаётся автоматически, однако это ограничение клиентской beta, а не серверная авторизация. В `Join.jsx` содержимое снимка отображается до присоединения.

Старый формат нельзя использовать для новой приватной модели. В MVP нужны случайный серверно проверяемый токен, срок действия, отзыв, ограничение повторного использования и доверенное принятие. Обычный ID встречи и декодируемый JSON не предоставляют права на чтение приватной встречи.

`requireOrganizer()` и `requireParticipant()` проверяют только изменяемую локальную роль. Их существующие unit-тесты проверяют бизнес-правила сервиса, но не безопасность от злоумышленника. Supabase должен независимо проверять `auth.uid()`, участие, организатора, авторство, допустимые переходы состояний и входные данные; RLS требуется проверять обычными пользовательскими сессиями.

## Фото, даты и адаптивный дизайн

`photos.js` принимает JPEG/PNG/WebP, до шести файлов по 2 МиБ, последовательно декодирует изображения, уменьшает длинную сторону до 1000 px, переводит в JPEG с качеством 0.72 (при необходимости 0.48). Сохранение дополнительно ограничивает число фото и форму data URL. Фото не имеют автора/Storage path; проверка MIME и canvas выполняется в браузере. Для MVP нужны приватный bucket, ограничения Storage, авторские записи, проверка участия и доступ к фотографиям через серверные политики.

Дата и время плана хранятся отдельными строками без IANA timezone; календарь использует floating local time. `createdAt`/`updatedAt`/`completedAt` берутся с часов браузера. Backend должен хранить `timestamptz`, явный timezone и отдельные серверные timestamps событий, не полагаться на часы клиента.

У приложения уже есть узнаваемый русский интерфейс: оригинальный логотип `public/brand/yavka-logo.jpg`, белые карточки, светло-голубой фон, синий акцент `#345eea`, скругления, карточки голосования, фирменные тексты и иллюстрация на главной. Desktop использует верхнюю навигацию, mobile — нижнюю; CSS содержит breakpoints, состояния фокуса и `prefers-reduced-motion`. Существуют toast, пустые состояния и подтверждение сброса Demo.

Это оценка исходников, а не новая визуальная проверка всех экранов. Сохранить `Brand`, существующие CSS и структуру карточек; добавлять Auth, друзей, чат, профиль и рейтинг в этот дизайн. Тексты «Без регистрации», «Никаких аккаунтов» и «Данные хранятся в вашем браузере» должны быть заменены после интеграции настоящего backend. Новый шаблон frontend не требуется.

## Отложенные модули

GPS, ИИ-гид, коллекция достопримечательностей, погода/ETA и push не обнаружены в исходной навигации или сервисах. Следовательно, нельзя сообщать об удалении их работающих реализаций. Нужно сохранить отсутствие этих зависимостей в активных сценариях и честно подписать ручное прибытие. Иконка `MapPin` обозначает текстовое место встречи; её наличие не означает геолокацию. Подробный итог после реализации — в `docs/DEFERRED_FEATURES.md`.

## Фактически выполненная проверка базовой версии

`npm test` завершился успешно на исходном сервисном слое: **17 тестов, 17 passed, 0 failed, 0 skipped**. Они проверяют seed, голосование, права локальных ролей, перенос плана, статусы, завершение, импорт снимка, защиту локальных данных, календарь и входные ограничения фото.

В исходном `e2e/yavka.spec.js` есть четыре сценария на двух проектах Playwright (desktop 1440×1000 и mobile 390×844): перенос приглашения в независимый browser context, lifecycle Demo, сброс Demo и адаптивная навигация. Они исследованы, но **не запускались как часть этого первоначального аудита**. README исходного коммита сообщает о прошлых успешных сборке и восьми browser-проверках; это не новые результаты текущего запуска и не проверка MVP с Supabase.

Регистрация, два настоящих аккаунта, приватность через RLS, общая встреча между устройствами, чат, Supabase Storage, серверный рейтинг и backend Realtime в базовой версии отсутствуют и не могут считаться проверенными. Последующая реализация и результаты сборки/E2E/SQL/RLS должны быть зафиксированы отдельно с фактическими passed, failed и непроверенными сценариями.
