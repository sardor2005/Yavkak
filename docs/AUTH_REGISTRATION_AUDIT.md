# Регистрация и предполагаемый предел двух аккаунтов

Дата: 12 октября 2026 года, Asia/Tashkent. Репозиторий: `sardor2005/Yavkak` (прежнее имя — `Yavka2`), ветка `fix/auth-registration-limits`; база PR — `496e750`, объединённый владельцем PR переноса №1. Текущий сайт: `https://yavkak.vercel.app`.

## Результат аудита

В активном frontend, регистрации, миграциях, триггерах и RLS **нет ограничения на два аккаунта**. Все новые UUID Supabase Auth получают собственный серверный профиль. Три независимых аккаунта успешно проверены на настоящем локальном Auth, через API и UI на desktop/mobile. RLS продолжает запрещать чтение и изменение чужих приватных данных.

Встроенный SMTP Supabase имеет другую квоту: **два Auth-письма в час на весь проект**. Подтверждения, восстановление пароля и другие Auth-письма расходуют её совместно. Встроенный отправитель также ограничивает адресатов участниками организации Supabase. Для обычных пользователей требуется custom SMTP с допустимой частотой отправки.

Пользователь сообщил, что третья регистрация выдаёт «лимит превышен», и не знает, подключён ли SMTP. Это согласуется с почтовой квотой. Однако точный облачный `error_code` и настройки SMTP пока не получены, поэтому причинность именно текущего production-отказа **не объявляется подтверждённой**. При общем `over_request_rate_limit` требуется проверять частоту Auth-запросов, а не автоматически менять SMTP.

## Воспроизведение механизма на настоящем Auth

В той же машине запущены отдельный GoTrue v2.186.0 и временная PostgreSQL-база. Письма поступали только в локальный Mailpit; основной Auth, база и контейнеры сохраняли исходные ID. Регистрация выполнялась обычным `/signup`, без административного создания пользователей и без отключения подтверждения.

| Почтовая квота временного Auth | Фактический результат |
| --- | --- |
| `GOTRUE_RATE_LIMIT_EMAIL_SENT=2` | Первые две регистрации: HTTP 200; третья: HTTP 429 и `error_code=over_email_send_rate_limit`. |
| `GOTRUE_RATE_LIMIT_EMAIL_SENT=100` | Три новые регистрации: HTTP 200; три настоящих письма Mailpit; подтверждены три независимые сессии и UUID. |

Временные Auth-контейнер, база и ровно пять диагностических писем удалены; основные пользователи и сервисы не менялись. One-off скрипт сохранён вне Git в `/tmp/yavka-auth-email-quota-proof.py`. Это воспроизведение внешней серверной квоты; оно не является чтением настроек облачного проекта.

## Изменение приложения

Обёртка Auth раньше выбрасывала `new Error(message)` и теряла код и HTTP-статус Supabase. Теперь `src/services/authErrors.js` сохраняет `code`, `status`, исходную причину и даёт отдельные русские сообщения для:

- `over_email_send_rate_limit`: временная квота писем, предложение повторить позже или войти уже подтверждённым аккаунтом.
- `email_address_not_authorized`: отправитель не доставляет письмо на выбранный адрес, требуется настройка владельцем.
- `over_request_rate_limit` / общий HTTP 429: частота запросов без утверждения о почтовой квоте.

Старые ответы без `code`, но с `email rate limit exceeded`, также распознаются. Другие ошибки сохраняют исходный текст. В код не добавляются лимиты количества пользователей, автоматические повторы регистрации или обходы подтверждения. SQL, RLS, grants и локальный конфиг не менялись.

## Что требуется в облачном Supabase

1. Получить код фактического отказа третьей регистрации из Auth Logs или ответа Auth API. Не передавать токен подтверждения, пароль и полный request body.
2. При `over_email_send_rate_limit` проверить SMTP Settings и Rate Limits. При `email_address_not_authorized` настроить custom SMTP для обычных адресатов. При общем request rate limit проверить частоту запросов и логи.
3. Подключить SMTP-провайдера и задать квоту в пределах его возможностей. Для custom SMTP Supabase первоначально устанавливает 30 писем в час; значение можно настроить. Использовать доступный бесплатный тариф без автоматического подключения платных расходов.
4. Сохранить email confirmation и RLS; проверить три разных реальных адреса, свежие письма, подтверждение, повторный вход и приватность данных. Локальные проверки не заменяют внешнюю доставку.

Прямой HTTP-доступ из этой среды к `yavkak.vercel.app` и облачному проекту не разрешён действующей сетевой политикой. Настройки SMTP и облачные логи недоступны; кодовый PR их не меняет. Поэтому снятие внешней квоты и три production-регистрации не объявляются выполненными. Инструкция владельцу с точными ссылками: [DEPLOYMENT.md](DEPLOYMENT.md).
