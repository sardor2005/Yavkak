# План продолжения MVP 1.0

Это сохранённый план задания, а не реализованная архитектура. Исходники отсутствуют; стек frontend, прежняя схема и правила рейтинга пока не установлены.

## Следующее обязательное действие

Получить существующие исходники сайта, повторить аудит и определить интерфейсы интеграции без замены дизайна. Затем утвердить схему и реализацию. Не создавать новый frontend вместо существующего.

## Восемь модулей

1. **Auth и профиль:** Supabase Auth, подтверждение email, восстановление пароля/сессии, редактирование собственного профиля; email не включается в публичный поиск.
2. **Встречи:** organiser-only изменения, отмена/завершение/история, `timestamptz` и явный timezone, серверное хранение.
3. **Приглашения:** друзья и безопасные случайные ссылочные токены со сроком действия/отзывом; доверенное принятие без раскрытия приватной встречи посторонним.
4. **Статусы:** отдельные состояния ответа на приглашение и прибытия; серверные timestamps, ручная отметка, Realtime.
5. **Фото:** приватный Supabase Storage, JPEG/PNG/WebP, сжатие, лимиты, проверка участия и авторства.
6. **Рейтинг:** сохранить установленные аудитом прежние правила, серверный расчёт, идемпотентность, отмена ошибок и учёт отменённых встреч; явно экспериментальный результат ручных отметок.
7. **Друзья:** публичный поиск, заявки и дружба без самодружбы/дублей, права владельцев и отсутствие утечки приватных полей.
8. **Чат:** только текст, проверка текущего участия, история с пагинацией, удаление своего сообщения, Realtime и синхронизация после восстановления сети.

## Данные и модель доступа

После аудита спроектировать единственные логические сущности `profiles`, `friend_requests`, `friendships`, `meetings`, `meeting_participants`, `meeting_invitations`, `attendance_events`, `meeting_photos`, `rating_events`, `chat_messages`.

Нужны UUID, FK, NOT NULL/UNIQUE/CHECK, индексы и `timestamptz`; конкретные поля пока не фиксируются вместо отсутствующей существующей модели. RLS применяется ко всем таблицам, доступным через API. Для доверенных операций использовать ограниченные PostgreSQL RPC или Supabase Edge Functions. Не добавлять отдельный постоянно работающий Node.js-сервер, Firebase или платные API.

Проверить предотвращение циклов RLS, запрет произвольного начисления баллов, повторной обработки и массовых запросов. Проверки авторизации обязательны на сервере; скрытие кнопки их не заменяет.

## Порядок реализации

Аудит исходников → схема и права → миграции/RLS → Auth → друзья/встречи/приглашения → статусы → чат → фото → рейтинг → отключение отложенных модулей → проверки и документация.

Публичные frontend-переменные, `.env.example`, конкретные команды установки/сборки и тестовые зависимости определить по существующему сборщику и lockfile. Доменные данные не хранить в localStorage; локальными могут оставаться настройки интерфейса и стандартное хранилище сессии Supabase Auth. Демонстрационные записи не переносить автоматически в реальные аккаунты.

## Контроль результата

Два реальных аккаунта на разных устройствах должны пройти общий сценарий встречи, приглашения, чата, ручных статусов, фото и рейтинга с сохранением данных после повторного входа. Пока ни один из этих этапов не реализован и не проверен.
