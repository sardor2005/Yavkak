# Подготовка развёртывания «Явки»

Приложение ещё не подготовлено к развёртыванию: подключённый репозиторий не содержит исходников приложения. Ни Supabase, ни Vercel не настроены и не проверены в рамках этой работы. Инструкция ниже описывает будущие действия владельца; она не заменяет проверенную конфигурацию проекта.

## 1. Найдите существующие исходники

1. Откройте в Vercel проект `yavka-rosy.vercel.app`.
2. В **Settings → Git** найдите подключённый GitHub-репозиторий и production branch.
3. Проверьте корневой каталог приложения в настройках сборки.
4. Предоставьте доступ к этому репозиторию или поместите существующий код в подключённый `sardor2005/Yavka-2.0`.
5. Сохраняйте существующий production deployment до завершения проверки MVP.

Исходные файлы необходимы для определения сборщика, установки по lockfile и сохранения дизайна. Восстановление приложения из скомпилированного сайта не заменяет эти исходники.

## 2. Supabase Free

После аудита и подготовки миграций:

1. Создайте проект на тарифе Free без подключения платных дополнений. Для интеграционных тестов используйте отдельный тестовый проект либо локальный Supabase; не проводите разрушительные тесты на production.
2. Примените подготовленные SQL-миграции в их порядке. Сейчас миграций в репозитории нет; точная команда будет добавлена после выбора совместимого инструментария.
3. Проверьте RLS всех пользовательских таблиц, grants и RPC под обычными аккаунтами, включая отрицательные сценарии. Привилегированный административный клиент не подтверждает корректность RLS.
4. Создайте приватный bucket фотографий с разрешёнными JPEG, PNG и WebP, ограничением размера и политиками доступа по участию во встрече. Конкретные имя bucket, лимиты и пути должны совпадать с миграциями и кодом.
5. Включите email/password Auth и подтверждение email. Проверьте доставку писем и ограничения штатной отправки на бесплатном тарифе до теста с двумя аккаунтами. Если ограничения отправки препятствуют регистрации, зафиксируйте это отдельно; не выдавайте локальное создание аккаунтов за проверенную доставку email.
6. Установите Auth Site URL `https://yavka-rosy.vercel.app`. Добавьте точные redirect URL существующего обработчика подтверждения email и восстановления пароля; пути определяются после аудита маршрутов. Для разработки разрешите только необходимый локальный адрес. Не добавляйте широкие wildcard-пути без необходимости.
7. Включите Realtime только для необходимых таблиц. Подписки в приложении должны фильтроваться по пользователю или разрешённой встрече и удаляться при выходе/размонтировании.

Supabase Free может приостанавливать неактивные проекты. Учитывайте действующие лимиты базы, Storage, подключения Realtime и отправки Auth-писем; проверяйте их в панели провайдера перед запуском.

## 3. Переменные и секреты

Имена переменных выбираются по фактическому сборщику, который пока неизвестен. Для Vite допустимы `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`, но это пример, а не подтверждённая конфигурация «Явки».

В браузере разрешены URL проекта и публичный publishable key, при условии проверенной защиты RLS. `service_role`, secret key, пароли базы и привилегированные токены запрещены в frontend bundle и в переменных с публичным префиксом сборщика. Значения секретов вводите в настройках соответствующего сервиса, а не в чат, Git или документы.

После получения кода будут подготовлены точный `.env.example` без значений и правила игнорирования локальных `.env`. Проверьте уже существующие файлы перед изменением.

## 4. Vercel Hobby и проверка

1. Сохраните текущий проект и домен; новый Vercel-проект не требуется.
2. После реализации добавьте подтверждённые публичные переменные для нужного окружения. Не добавляйте административные ключи в frontend.
3. Сначала проверьте feature branch в preview при наличии нужного доступа. Добавьте в Supabase только нужные callback URL этого тестового deployment.
4. Выполните сборку и интеграционные проверки по `docs/TESTING.md`.
5. Проверьте двух реальных пользователей на двух устройствах, повторный вход, приватность встречи и фото, Realtime и запрет изменения чужих данных.
6. Подготовьте и проверьте PR. Merge и production deployment выполняются владельцем после проверки; в этой работе они не выполнены.

После изменения переменных Vercel требуется новое развёртывание, чтобы сборка получила значения. Проверка существования переменных не подтверждает успешное соединение с Supabase.

## 5. Резервное копирование без платных функций

После утверждения схемы настройте ручной экспорт базы через совместимый Supabase CLI/PostgreSQL-инструментарий и отдельный экспорт объектов приватного Storage через авторизованный административный инструмент. Уточните охват Auth, схемы Storage и метаданных: обычный дамп прикладных таблиц не сохраняет содержимое фотографий и не гарантирует полный перенос аккаунтов.

Храните резервные копии вне публичного репозитория, с ограничением доступа. Проверяйте восстановление в отдельной среде и совпадение метаданных фотографий с объектами. Не полагайтесь на наличие платного автоматического backup. Точные проверенные команды можно зафиксировать только после получения проекта и доступа к тестовой среде.
